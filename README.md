# Hook Lab — нові хуки для модифікацій SockLock

**Проблема.** Motion-дизайнер витрачає ~3 год на одну модифікацію, з них близько половини йде на ручне переписування хуків, перших фраз і тексту на екрані за скриптом переможця. Через це команда впирається в ~240 модифікацій на місяць, а для $800k spend їх потрібно ~500.

**Рішення.** Утиліта приймає скрипт-переможець і за ~30 секунд видає 10 варіантів нового відкриття ролика: хук, перша фраза, текст на екрані, ідея візуалу. Кожен варіант проходить автоматичну перевірку, зламані виправляються автоматично. Дизайнер обирає варіанти, за потреби править їх і експортує бриф.

## Швидкий старт

Потрібен Node.js **22.18+**: він запускає TypeScript напряму, без збірки.

```bash
npm install
cp .env.example .env      # впишіть ANTHROPIC_API_KEY
npm start                 # → http://localhost:3000
```

**Без ключа** утиліта працює в mock-режимі: відтворює записану справжню відповідь моделі для скрипту «Tiny magnet» (`data/mock/`). Увімкнути mock примусово можна через `MOCK=1 npm start`.

## Як користуватись

**Веб-сторінка** (основний сценарій для дизайнера):

1. Вставте скрипт-переможець або натисніть кнопку з прикладом.
2. За бажанням задайте тему, кількість варіантів і кути хука. Без обраних кутів беруться всі, найкращі за ROMI ідуть першими.
3. **Generate variants**: за ~30 с з'являються картки зі статусами *Ready / Check / Error*.
4. Позначте **Use** на потрібних варіантах. Якщо правите текст, лічильник слів і перевірка оновлюються одразу.
5. **Export brief**: бриф у Markdown для дизайнера і CSV для імпорту в Airtable. Файли також зберігаються в `out/`.

**Командний рядок:**

| Команда | Що робить |
|---|---|
| `npm run generate -- data/scripts/winner-1-tiny-magnet.txt` | Варіанти + бриф з одного скрипту. Опції: `--count 5`, `--angles demo,pain`, `--select 1,3`, `--mock`, `--json` |
| `npm run stats` | Метрики пілоту з логу веб-сесій (`logs/sessions.jsonl`). Опція `--mock` включає mock-прогони |
| `npm run eval` | Порівнює версії промпту на всіх прикладах скриптів (потрібен API-ключ). Звіт пишеться в `eval/` |
| `npm test` | 51 тест, без мережі й ключа |
| `npm run typecheck` | Перевірка типів |

## Як це працює

```
скрипт-переможець ─┐
data/winners.csv ──┼─► промпт ─► Claude (JSON-схема) ─► перевірка ─► автовиправлення ─► вибір дизайнера ─► бриф .md / .csv
data/brand.json ───┘                                                                         └─► logs/sessions.jsonl
```

1. **Бібліотека переможців.** З `winners.csv` рахується ROMI кожного кута, зважений на spend. У промпт іде 6 прикладів: лише переможці (ROMI ≥ 125%, spend ≥ $5k), спершу з тієї ж теми, не більше 2 на один кут.
2. **План кутів.** Кожному слоту призначається кут, кращі за ROMI ідуть першими.
3. **Генерація.** Claude Sonnet 5.5 зі structured output: відповідь гарантовано відповідає JSON-схемі.
4. **Перевірка без LLM.** Детермінована і покрита тестами:
   - ліміти слів: хук ≤ 12, текст на екрані ≤ 7, перша фраза ≤ 20;
   - заборонені формулювання з `brand.json` (free, guarantee, forever, …);
   - ціна лише $29;
   - числа, схожі на вигадану статистику, отримують попередження;
   - схожість з оригіналом і дублікати в партії (Jaccard ≥ 0,6);
   - відповідність кута плану.
5. **Автовиправлення.** Варіанти з помилками один раз повертаються моделі з конкретною причиною, наприклад «Hook is 14 words, limit 12». Потім перевірка повторюється. Попередження лишаються на розсуд людини.
6. **Бриф і лог.** Дизайнер обирає й править варіанти, бриф експортується, а сесія пишеться в лог для метрик.

## Структура

```
data/            бізнес-дані, які редагує маркетолог, а не код
  brand.json     факти продукту, ліміти, заборонені формулювання
  winners.csv    бібліотека минулих хуків з метриками (синтетична, 30 оголошень)
  scripts/       3 скрипти-переможці для прикладу
  mock/          записані справжні відповіді моделі для роботи без ключа
public/          веб-сторінка (один HTML-файл, без збірки)
src/
  domain/        чиста логіка без I/O: кути, бібліотека, перевірка, бриф, метрики, звіт eval
  llm/           робота з моделлю: промпти, JSON-схеми, розбір відповіді
                 hook-writer.ts — інтерфейс; anthropic-writer / mock-writer — дві реалізації
  infra/         файли, .env, лог сесій
  use-cases/     сценарії: generate-variations, export-brief, run-eval
  http/          JSON API для сторінки (Hono)
  bootstrap.ts   єдине місце, де обирається справжня модель чи mock
  cli.ts, server.ts   точки входу
```

Принципи:
- `domain` не знає про файли, мережу і модель, тому тестується миттєво.
- Модель схована за інтерфейсом `HookWriter`: mock і фейкова модель у тестах підставляються без змін у логіці.
- Веб і CLI викликають ті самі use-cases.
- Тести лежать поруч із модулями (`*.test.ts`) і запускаються вбудованим `node --test`.

## Вартість і швидкість

Один прогін (10 варіантів) коштує **$0,03–0,06** і триває **25–45 с** (Sonnet 5.5: $2 / $10 за млн токенів). На 500 модифікацій на місяць це ~50–100 прогонів, тобто **~$3–6 на місяць**. Найближча готова альтернатива, LLM-підписка для 6 дизайнерів, коштує ~$150 на місяць і не має бібліотеки переможців, перевірки та вимірювання.

## Як міряємо успіх

| Метрика | Зараз | Ціль | Коли | Як міряємо |
|---|---|---|---|---|
| **Час дизайнера на модифікацію** (основна) | ~3 год | ≤ 1,8 год | 2-тижневий пілот | 2 дизайнери з утилітою проти 4 без неї; таймтрекінг задач в Airtable |
| Модифікацій на дизайнера | 40 / міс | ≥ 65 / міс | через місяць | Кількість задач в Airtable |
| Частка прийнятих варіантів (рання ознака) | — | ≥ 30% | перший тиждень | `npm run stats`: обрані в бриф / згенеровані |
| Час від генерації до експорту | — | медіана ≤ 10 хв | перший тиждень | `npm run stats` |
| Валідні варіанти | — | ≥ 95% після автовиправлення; ≥ 50% «usable» за ручною рубрикою | до пілоту | `npm run eval` |
| ROMI модифікацій з нових хуків (обмежувач) | 140% | не нижче 140% | 4–6 тижнів | Експорт Meta за ad_id з брифу |

Якщо основна метрика досягає цілі, ті самі 720 год дизайнерів дають ~400 модифікацій замість 240. Це **+$43k EGP на місяць** у базовому сценарії (діапазон $15–83k). Розрахунок — у документі з кроками 1–4.

## Результати перевірки якості

Перший живий прогін на «Tiny magnet» показав, що модель погано рахує слова: 2 з 10 хуків вийшли за ліміт. Ціль у промпті «≤ 10 слів, порахуй перед відповіддю» дала 0 помилок, але прогін подвоївся в часі й ціні:

| Версія промпту | Помилок з 10 | Час | Вартість |
|---|---|---|---|
| Лише жорсткий ліміт | 2 | 23 с | $0,031 |
| Ціль нижче ліміту + «count them» | 0 | 43 с | $0,064 |

Яку версію лишити, вирішує `npm run eval`: він порівнює `count` і `margin` (ціль без «count them») на всіх трьох скриптах. Звіт із кожним варіантом і колонкою для ручної оцінки зберігається в `eval/`.

## Обмеження MVP

- Дані синтетичні: `winners.csv` і скрипти складено за цифрами з дата-руму, а не взято з реального кабінету.
- Mock відтворює відповідь для одного скрипту, «Tiny magnet».
- Сесії веб-сервера живуть у пам'яті; після перезапуску потрібно згенерувати заново.
- Заборонені формулювання — простий список, а не повна перевірка політик Meta.

## Наступна ітерація

1. **Зворотний зв'язок із результатами.** Імпорт CSV-експорту Meta за ad_id з брифу автоматично оновлює `winners.csv`. Кути з вищим ROMI і вищою часткою прийняття отримують більше слотів.
2. **Airtable.** Бриф створюється одразу як задачі дизайнерам, без імпорту CSV.
3. **Матриця модифікацій.** Варіації не лише перших 3 секунд, а й CTA і тексту на екрані посеред ролика.
4. **Локалізація DE/FR на тому ж ядрі.** Новий use-case і `brand.json` для кожної мови.
5. **Продакшн.** Авторизація, база замість JSONL, деплой для всієї команди.
